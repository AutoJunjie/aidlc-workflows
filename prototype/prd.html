AI-DLC 多人协作交互原型 PRD

产品需求文档 v1.0

一、背景与问题

1.1 现状痛点

在使用 AI-DLC 进行团队开发时，存在明显的协作瓶颈：

当前模式：
┌─────────────────────────────────────────────────────┐
│                    共享屏幕                          │
│  ┌─────────────────────────────────────────────┐   │
│  │          AI-DLC CLI / IDE                   │   │
│  │                                             │   │
│  │  Q: 您希望使用哪种数据库？                    │   │
│  │  A) MySQL  B) PostgreSQL  C) DynamoDB       │   │
│  │                                             │   │
│  │  [Answer]: _                                │   │
│  └─────────────────────────────────────────────┘   │
│                       ▲                            │
│         ┌─────────────┼─────────────┐              │
│         │             │             │              │
│      张三口述      李四口述      王五口述           │
│      "我觉得A"    "B更好吧"    "C适合我们"         │
│                       │                            │
│                       ▼                            │
│                   操作者输入                        │
│              （信息损失、效率低下）                  │
└─────────────────────────────────────────────────────┘

核心问题：

  1. 只有一个人能输入，其他人只能口述
  2. 意见容易被遗漏或误解
  3. 讨论过程无记录，决策依据不清晰
  4. 无法直观看到每个人的观点和倾向

1.2 目标用户

  • Tech Lead / 架构师：主持讨论，做最终决策
  • 开发工程师：参与讨论，表达技术意见
  • 产品经理：参与需求澄清环节
  • 团队规模：4-6人

二、产品目标

2.1 核心目标

构建一个多人实时协作界面，让团队成员能够：

  • 各自独立输入意见
  • 实时看到他人观点
  • 由 Tech Lead 汇总决策
  • 结果无缝对接 AI-DLC

2.2 设计原则

原则说明
低门槛打开浏览器即可使用，无需安装
实时同步所有人看到相同的讨论状态
角色明确主持人控节奏，决策者拍板
可追溯每个决策都有讨论记录

模块A：房间系统

A1. 创建房间

  • 输入：房间名称、我的昵称、选择角色（Tech Lead / 成员）
  • 输出：生成6位房间码
  • 规则：创建者默认为主持人

A2. 加入房间

  • 输入：房间码、我的昵称
  • 输出：进入协作界面
  • 规则：最多6人，超出提示已满

六、数据结构

6.1 房间状态

interface Room {
  id: string;              // 6位房间码
  name: string;            // 房间名称
  createdAt: Date;

  participants: Participant[];

  // 当前内容
  currentContent: QuestionContent | ReviewContent | null;

  // 讨论状态
  discussionState: 'open' | 'locked' | 'decided';

  // 历史记录
  decisions: Decision[];
}

interface Participant {
  id: string;
  name: string;
  role: 'tech_lead' | 'member';
  isHost: boolean;         // 是否主持人
  isOnline: boolean;
  joinedAt: Date;
}

6.2 意见与决策

interface Opinion {
  participantId: string;
  choice: string;          // 'A' | 'B' | 'C' | 'D' | 'X'
  reason: string;
  submittedAt: Date;
  updatedAt: Date;
  status: 'draft' | 'submitted';
}

interface Decision {
  questionId: string;
  choice: string;
  rationale: string;
  decidedBy: string;       // participantId of Tech Lead
  decidedAt: Date;
  opinions: Opinion[];     // 快照：决策时的所有意见
}

七、Demo 原型技术方案

7.1 技术选型（纯前端）

技术选择理由
框架纯 HTML/CSS/JS零依赖，打开即用
样式内联 CSS单文件分发
P2P通信PeerJS (WebRTC封装)无需后端，房间码连接
数据格式JSON标准化

7.2 原型范围

包含：

  • 创建/加入房间
  • 参与者列表实时更新
  • 问题展示和意见输入
  • 意见实时同步（模拟）
  • Tech Lead 决策功能
  • 主持人流程控制

不包含：

  • 真实的 CLI 集成
  • 数据持久化
  • 用户认证

八、验收标准

8.1 功能验收

#功能点验收标准
1创建房间输入信息后生成6位房间码
2加入房间输入房间码后进入协作界面
3参与者同步新成员加入，所有人列表更新
4意见输入选择选项+填写理由，点击提交
5意见同步提交后其他成员实时看到
6统计更新每次提交后，统计条自动更新
7锁定讨论主持人锁定后，成员无法修改
8最终决策Tech Lead 选择+理由，确认决策
9切换问题主持人可切换到下一个问题

8.2 体验验收

#体验点验收标准
1响应速度意见同步延迟 < 500ms
2状态可见明确知道谁在输入、谁已提交
3角色区分Tech Lead 和成员看到不同的控件
4流程清晰知道当前在哪一步，下一步是什么
